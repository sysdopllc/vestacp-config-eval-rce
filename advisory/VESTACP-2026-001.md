# VESTACP-2026-001 — VestaCP ≤ 0.9.8-26: authenticated config-parser `eval` sinks → privilege escalation to root

| | |
|---|---|
| **Product** | Vesta Control Panel (VestaCP) |
| **Affected versions** | ≤ 0.9.8-26 (all releases shipping the `eval`-based config parser) |
| **Severity** | Critical — CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H = **9.9** |
| **Type** | CWE-78 (OS Command Injection) / CWE-95 (Improper Neutralization of Directives in Dynamically Evaluated Code — `eval`) |
| **Vendor status** | Unmaintained — last upstream release 0.9.8-26 (September 2019); no fix exists |
| **Reporter** | Bryan Ramirez — SYSDOP LLC |

## Summary

VestaCP stores per-account objects (domains, cron jobs, DNS, mail, users) as
`KEY='value'` lines under `$USER_DATA/*.conf`. The shared shell library
`func/main.sh` — sourced by every `v-*` administration script, **all of which
run as root** — parses those lines with `eval`, so the assignments land in the
calling shell's environment.

Values in those files are controllable by an **authenticated panel user**
(cron command fields, domain/alias fields, DNS and mail records, display
names and comments). Any value that lands with an **unescaped single quote**
breaks out of the quoted assignment and injects arbitrary shell, executed as
**root** the next time any `v-*` script parses that object — which happens on
routine panel operations and on cron-driven sync jobs, without further
interaction.

This is the same sink class published for VestaCP's downstream fork
**HestiaCP** as
[GHSA-w3mx-xq85-8qqc](https://github.com/hestiacp/hestiacp/security/advisories/GHSA-w3mx-xq85-8qqc)
(config parser `eval` → root RCE, fixed in 1.9.5),
[GHSA-cr7q-frhq-xw4v](https://github.com/hestiacp/hestiacp/security/advisories/GHSA-cr7q-frhq-xw4v)
and
[GHSA-5fpv-c8rg-x6r3](https://github.com/hestiacp/hestiacp/security/advisories/GHSA-5fpv-c8rg-x6r3)
(unquoted cron argument → crontab injection). Hestia patched the class in the
fork; **VestaCP itself never received an advisory or a fix** and remains
deployed worldwide — notably in VPS templates (e.g. Virtualizor images) still
offered by hosting providers today.

## Affected sinks (`/usr/local/vesta/func/main.sh`, 0.9.8-26)

| Function | Sink | Effect |
|---|---|---|
| `is_object_value_empty` | `eval "$object"` over `grep` result of `$USER_DATA/$1.conf` | executes conf line as shell |
| `is_object_value_exist` | same pattern | executes conf line as shell |
| `get_object_value` | same pattern | executes conf line as shell |
| `update_object_value` | same pattern | executes conf line as shell |
| `add_object_key` | same pattern | executes conf line as shell |
| `search_objects` | `eval $line` per matching line | executes conf line as shell |
| `sync_cron_jobs` | `eval $line` over every line of `cron.conf` | executes conf line as shell |
| ARGUMENTS builder | `eval echo \$${I}` | indirect eval of argument expansion (also a latent glob-expansion bug) |
| `is_format_valid` | `eval arg=\$$arg_name` | indirect eval of validated value |
| `bin/v-add-cron-job` | `echo $7` unquoted | raw newlines/metacharacters from `$7` land in the user's crontab (GHSA-5fpv class) |

The central pattern (verbatim shape in stock 0.9.8-26):

```bash
get_object_value() {
    object=$(grep "$2='$3'" $USER_DATA/$1.conf)
    eval "$object"                       # <- sink: executes conf contents
    eval echo \$${4#\$}                  # value returned via second eval
}
```

## Exploitation path

1. Attacker holds an ordinary authenticated VestaCP account (hosting
   customer) or any write path that lands data in `~/conf/*.conf`
   (panel fields that bypass `%quote%`/`%dots%` escaping, backup/restore,
   API/import paths).
2. A crafted value containing an unescaped `'` is stored, e.g. in a cron
   `CMD` field: `CMD='x'; id > /tmp/pwned; #`.
3. On the next root-run `v-*` invocation that parses the object
   (`get_object_value`, `sync_cron_jobs`, listing/restore/update paths), the
   `eval` runs the injected commands **as root**.

Confirmed locally: a crafted `'` in a parsed conf value caused `eval` to
execute a command, creating a marker file.

**Impact:** tenant-to-host escape — full root on the node, exposing every
site, mailbox and database of every account it hosts.

See `poc/poc-eval-sink.sh` for a self-contained demonstration that simulates
the vulnerable parse and shows the hardened parser neutralizing it.

## Additional finding (functional bug, not the vulnerability)

While certifying equivalence of the hardened parser (1,165 field comparisons
against real `web`/`dns`/`mail`/`cron`/`user`/`db` confs): the stock
`eval echo $4` path performs **glob expansion** — a literal `*` in a field is
expanded to a directory listing instead of being returned verbatim. The
non-eval parser returns `*` correctly; the replacement is therefore
equivalent **and** fixes a latent parsing bug.

## Mitigation

No upstream fix exists — VestaCP is unmaintained since 2019. Operators still
running it should apply one or more of:

1. **Replace the `eval` parser** with a non-eval key/value parser.
   `mitigation/non-eval-parser.sh` provides a drop-in
   `parse_object_kv_list` (strict `KEY='value'` regex extraction + `declare -g`
   assignment — values become literals, never executed) plus a converted
   `get_object_value` as reference for porting all seven eval sites.
2. **Enforce escaping** on every `v-*` entry point that ingests user data
   (`%quote%` for `'`, `%dots%` for `:`), and quote every expansion
   (`echo "$7"` in `v-add-cron-job`).
3. **Restrict the panel** (firewall/IP allow-list on the panel port) and
   monitor `$USER_DATA/*.conf` for unexpected writes.
4. **Migrate** to a maintained control panel.

- **2026-08** — sinks identified, PoC confirmed and in-house remediation
